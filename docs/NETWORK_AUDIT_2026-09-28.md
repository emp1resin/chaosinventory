# ChaosInventory: расследование загрузки и отправки отчётов

Дата: 28 сентября 2026. Проверяемая production-версия: `a93516fc06f53ebb2a1a17dbafc89b9fa05266a8`.

## Вывод

Первый источник профиля `chaosage.space/getAvatarsDataByName` действительно отвечает HTTP 403 без CORS. Поэтому браузер сайта получает `TypeError: Failed to fetch`, скрывая сам HTTP-ответ. Это подтверждено запросом, а не предположением по тексту ошибки.

Резервный сервер во время проверки отвечал нормально. Причина его отказа у конкретного игрока пока не установлена. Проверки из GitHub Actions и нашей браузерной сессии не доказывают доступность из сети этого игрока.

Каталог сохранённых профилей ограниченного числа ников не решает задачу примерочной: нужны текущие данные произвольного персонажа. Его использование как незаметной замены свежего профиля следует убрать в согласованном исправлении.

В этом расследовании основной сайт и backend не изменены. Подготовлены отдельная ветка, тесты и диагностическая страница. Тесты существующих дефектов подтверждают их воспроизведение; они НЕ означают, что дефекты уже исправлены.

## Откуда берутся данные

| Данные | Источник и путь |

| Религия и место в клане | `sAPI2.php`: `user_fraction`, `clan_list_by_user_name` |

Из этого следует общий риск: недоступность bridge одновременно лишает игрока запасного профиля и возможности отправить отчёт. GitHub Pages отдаёт статику; backend находится на другом домене.

Отдельно в нашей браузерной сессии загрузилась Ашалинда с 11 предметами. Это проверка нашей сессии, не подтверждение исправления у другого игрока.

## Воспроизведение отказов текущего кода

Файл: `site-source/scripts/test-network-failures.mjs`.

Команда из `site-source`:

```bash
node --experimental-vm-modules scripts/test-network-failures.mjs
```

Сетевые ответы подменяются в изолированном окружении; тесты не обращаются к игре.

| Сценарий | Результат |
|---|---|
| Первый источник 403, bridge работает | Живой профиль получен |
| Оба источника недоступны, нового ника нет в кеше | Импорт невозможен; ограниченный каталог не спасает |
| Первый источник вернул `{"out":{}}` | Дефект: пустой профиль принимается как успешный |
| Рейтинг кланов завис | Дефект: запрос не ограничен тайм-аутом; импорт ожидает его через Promise.all |
| Bridge прислал заголовки, тело ответа зависло | Дефект: таймер очищен до чтения тела; профиль может зависнуть. Проверено с ускоренными таймерами после истечения срока |
| Прямой API вещей недоступен, bridge работает | Получение данных через bridge работает |
| Первый отчёт в очереди отклонён HTTP 413 | Дефект: очередь останавливается, следующий корректный отчёт не отправляется |
| Допустимые по отдельности поля диагностики заполнили буфер | Дефект: итоговый JSON может превысить серверный лимит 24 000 байт |

Кнопка сейчас отправляет в очередь любые ошибки, включая постоянные 400/413/415, и обещает отправку после восстановления связи. Для постоянной ошибки формата/размера эта формулировка неверна.

При анализе также найдены:

- Отсутствие ID сборки в отчёте: трудно установить, какой JavaScript был открыт у игрока.
- Кеширование rejected Promise руны Разлома на время сессии: временная ошибка сохраняется при повторной загрузке. Это найдено чтением кода, отдельного регрессионного теста пока нет.
- Кратковременный HTTP-кеш bridge для профиля и предметов: повторное получение может быть несвежим. Для режима «обновить текущего персонажа» требуется явная политика свежести на клиенте и сервере.
- Ошибка одного предмета прерывает импорт целиком. Нельзя при этом молча считать персонажа полностью загруженным без этой вещи; следует указывать слот и давать повторить запрос.

## Что изменилось после утреннего отказа

1. При отказе chaosage.space добавлен путь через сервер к публичной странице игры.
2. Для API предметов добавлен резервный сервер; уточнены этапы ошибок.
3. Добавлены кнопка отчёта и очередь повторной отправки на тот же backend.
4. Пробовался прямой запрос публичной страницы из браузера; отсутствие CORS не позволило использовать его.
5. Добавлен конечный каталог профилей на GitHub Pages. Он не отвечает требованию свежего импорта любых персонажей.

Ссылки с `?v=…` на один и тот же GitHub Pages — не две независимые версии приложения. Параметр в ссылке не переключает серверные endpoints и не изолирует изменения. Для сравнения нужны отдельные пути/сборки с видимым номером версии.

## Подготовленная страница для проверки у игрока

Файл `diagnostics/index.html`, ещё не опубликован.

- Ввод любого ника, одно нажатие; скачивание файлов и текстовое объяснение не нужны.
- Проверка старого источника, live bridge, религии, клана, славы, текущего списка вещей, каждого надетого ID и рун Разлома.
- Повторное получение списка ID позволяет заметить, что игрок переоделся во время проверки. Изменение модификаций того же ID этим сравнением не выявляется.
- Отдельно проверяются GET, простой POST и JSON POST с preflight.
- HTTP-ошибка, сетевой отказ, тайм-аут, неверный JSON и неправильный формат списка не подменяют друг друга.
- При доступном endpoint страница сама отправляет ограниченный по размеру отчёт и показывает квитанцию. Если endpoint недоступен, результаты видны на странице; заявлять об успешной отправке нельзя.
- Профили из конечного каталога не используются. `cache: no-store` задан на клиенте; серверные правила кеша этой страницей не изменяются.

Дополнительные 4 проверки страницы прошли локально: произвольный ник и 11 вещей с руной; полный сетевой отказ без ложной квитанции; неправильный список не превращается в «голого» персонажа; смена предмета в процессе выявляется. Синтаксис JavaScript проверен. Публикация и проверка в браузере пострадавшего игрока ещё предстоят.

## Варианты исправления для согласования

### A. Сохранить GitHub Pages, исправить и сделать доступным live backend

Получать профиль любого ника с открытой страницы игры через сервер, вещи — по текущим ID экземпляров. Убрать конечный каталог как автоматическую замену свежему профилю; ограничить каждый этап вместе с чтением тела; проверять обязательные поля; сбрасывать неудачный кеш рун; корректно классифицировать ошибки отчётов и ограничивать их размер. Добавить ID сборки и источники/время данных.

Если bridge-домен недоступен из сети игрока, сменить доступный ему домен/хост backend. Простая замена надписи или увеличение тайм-аута не исправляет недоступный домен. Перед выбором хоста проверить его с того же устройства и сети.

### B. Сайт и backend на одном доступном домене

Развернуть калькулятор и `/api/…` вместе, игра опрашивается сервером. Это устраняет необходимость CORS между калькулятором и своим backend. Не устраняет отказ внешней игры или недоступность самого хоста. Перенос требует согласования и проверки нового адреса игроком; основной сайт сохраняется до успешной проверки.

### Что уже проверено и не подходит как самостоятельное решение

- Прямой `showInfo.php` из браузера: HTTP 200, но нет CORS.
- Конечные сохранённые профили: не обеспечивают произвольные ники и свежие данные.
- Откат только frontend: не восстановит endpoint chaosage.space, который сейчас отвечает 403.
- Повторная отправка того же отчёта после постоянного 413: снова будет отказ.
- Простое использование POST text/plain сейчас: backend отвечает 415; для этого варианта необходимы согласованные изменения сервера, и он не поможет при недоступности домена.

## Чего ещё не хватает

Нужна трасса именно неуспешной попытки из браузера игрока. В доступном вложении — текст сообщения из игрового чата об ожидающем отправки отчёте, а не Console/Network Chrome. Полученный пользовательский отчёт с Djan описывает успешный импорт и не объясняет следующую неудачную попытку.

Минимум: точный адрес открытого сайта, ник и скрин красных строк Chrome Console после повторения ошибки. Сравнение с другой сетью/VPN поможет отделить сетевой отказ, но само по себе не назовёт причину. Код сайта не получает подробности CORS/сетевых блокировок, которые Chrome показывает в Console/Network.

Следующий согласуемый шаг: опубликовать **только** подготовленный `diagnostics/index.html` отдельным коммитом, без объединения всей ветки и без пересборки калькулятора. После результата выбрать A или B и подготовить отдельную проверяемую версию исправления. Нельзя объявлять текущую проблему игрока решённой до такой проверки.
